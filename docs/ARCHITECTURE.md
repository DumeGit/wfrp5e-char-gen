# Application structure and shared results

`dist/app.js` owns boot, the current draft/catalogue, transient browsing state, event wiring and shell composition. Feature factories in `dist/features/` own shared controls, Origins, creation views, Experience, shop, review, dialogs, creation resets, actions and the workspace shell. Factories receive a live context; assigning a replaced draft/catalogue or UI preference immediately publishes it through the explicit state setter. Book mechanics remain named handlers in the supplement modules. No book JSON executes code.

`character-result.mjs` produces the common derived scores, load/equipment result, purse, effective Career, Skill rows, known magic/runes/techniques/Cants, compact gear summaries and issues. Equipment summary formatting lives in `folio-gear.mjs` to keep the calculation layer independent of the folio renderer. The app caches one snapshot per serialized draft revision and catalogue identity. In-place changes, undo and book switches invalidate it. Folio and review consume the same Skill rows; both PDF exports receive this same result, and the appended record reuses the sheet's result. Independent export callers can omit the result and calculate once. Eligibility/price quote handlers remain explicit rules; they are not replaced by presentation calculations.

Issues carry `{code, message, severity, source, control: {step, target}}`. Rule validators create codes and destinations where failures are detected; routing never reads message wording. Warnings and information do not block purchases/export. String-returning rule APIs remain for existing integrations/tests; the application requests structured records. Do not add a message-regex routing fallback. Correct a target at its rule source, keeping it in sync with the actual control. Book/page metadata drives source buttons; displayed source labels are never parsed to discover their destinations.

`content-references.mjs` contains reviewed exact aliases with their kind, source, scope and decision. `resolveContent` accepts an active `contentId` or an unambiguous scoped name and rejects ambiguity/unavailable content. A name does not select between Career variants. No fuzzy mapping or general Fourth Edition conversion is permitted. Existing equipment bundle parsing, contextual Ogre sizing and unusual book mechanics remain explicit handlers.

Expandable sections use `data-detail-key`, composed by `detailKey(section, entry)`. Content IDs are preferred; otherwise use an explicit stable key/name in that section. Capture/restore uses this key only, never a summary's English text. Repeated sections must include content identity; don't use positional row numbers or a translated label as identity.

`book-search.mjs` indexes the assembled selected catalogue, including supported specialisations and exact scoped aliases. Equipment joins exact-name profile/shop facets within a book; a search record retains each facet's content identity and source. Search ranking is pure/read-only. `features/book-search.mjs` owns the persistent banner field, dropdown and a separate reference dialog, so keystrokes do not rerender the workspace or mutate the draft. Navigation routes use the shared result and existing quote handlers, rechecking against the live character before opening existing controls; no creator-status section appears in references. `book-search-links.mjs` matches exact related catalogue names and resolves same-book targets or explicit alternatives. The feature owns transient dialog history and hover/focus previews. Catalogue identity changes invalidate the index, chain and open reference. Shared Talent and magic detail bodies are reused rather than importing separate rule descriptions. See [BOOK-SEARCH.md](BOOK-SEARCH.md).

The registry loads each book's reviewed `coverage.json`. Generated source inventories include profiles even if combined-book precedence withdraws them. Active catalogue counts apply those precedence decisions. Catalog records and chapter/features have separate counts; supporting a learnable spell profile does not claim live spellcasting automation. Details and maintenance commands are in [BOOKS.md](BOOKS.md) and [INCLUSION-MATRIX.md](INCLUSION-MATRIX.md).

## Shared presentation system

`design-tokens.css` and `design-system.css` load after feature styles and own the Black Banner visual contract. `design-system.mjs` provides safe, accessible page-heading and emblem markup. Creation views and book setup use its common heading, while the shell uses the common emblem. Motion follows the OS preference through CSS. `install-control.mjs` keeps the same browser-owned Install app button when mounting it into each new rail, preserving PWA listeners and state across redraws; `pwa.mjs` continues to own install/update behavior. Fonts/art/icons and the standalone component guide are included by the recursive offline build. Future features use shared roles/controls instead of copying visual preview code; see [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md).

## Separate GM creator

`npc.html`/`npc-app.mjs` own the independent GM draft, reviewed book selection, transient filters, recorded actions and session undo. `features/npc-views.mjs` composes eight focused views: profile, Characteristics, Traits/mutations, Skills/Talents, equipment, magic, Career development and review. Shared controls/references live in `npc-controls.mjs`; `npc-shell.mjs` owns rail/mobile navigation and folio; `npc-feedback.mjs` renders early blocking issues and nonblocking source notes. `npc-flow.mjs` declares section IDs and target-based issue routing, with no English-message matching. `npc-state.mjs` owns validated JSON/state; `npc-profile.mjs` handles sourced profile parsing and choice expansion; `npc-result.mjs` calculates one result with structured issues and explicit XP quotes. `npc-sheet.mjs` builds one compact play-facing model for review/text/PDF; `npc-pdf.mjs` lays out its paginated stat sheet. `npc-export.mjs` enforces export readiness and provides compact text/PDF and separate audit backups. Discrepancy and Legacy explanations remain in the app, outside the compact sheet. It does not use the PC AcroForm or a fabricated PC Species/creation history. The registry's four Bestiary arrays are validated by `bestiary-content.mjs` and indexed by shared book search. NPC search passes `referenceOnly` so player eligibility/route handlers never inspect NPC state. See [NPC-CREATOR.md](NPC-CREATOR.md).

`talent-targets.mjs` shares explicit Cause parsing, placeholder validation and Career eligibility between PC/NPC purchases; `talent-targets-ui.mjs` provides the PC choice control. `npc-training.mjs` resolves profile-specific training choices and selected reference provenance. `deft-steps.mjs` attaches reviewed Miracle replacements to their aspect lists without marking or modifying global core Miracle definitions. `career-variants.mjs` supports multiple mutually exclusive profiles for a Career and preserves the existing Species/identity reset boundary.
